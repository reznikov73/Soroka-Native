# TASK-N04 — Фаза 2, срез 2: сплиттеры панелей

Дата: 2026-11-18. Версия: 0.3.2. Предыдущая задача: TASK-N03 (v0.3.1).

## Постановка

Эталон — Soroka TASK-012 (свободная компоновка панелей): ряд
[Папки | Письма | Письмо], между панелями сплиттеры `.splitter-v` (6px,
курсор col-resize, полоса-хват 3×36px, подсветка при наведении).
Перетаскивание меняет веса только соседней пары панелей (минимум панели
110px, сумма весов пары сохраняется), двойной клик возвращает весам пары
дефолт (LAYOUT_DEFAULTS: folders 0.2827 / list 1.2443 / reading 2.023 —
«узкие папки, широкое письмо», согласовано с пользователем в октябре
2026), компоновка сохраняется (в Soroka — localStorage `soroka.layout2`).

Нативной оболочке нужны те же сплиттеры: сейчас ширины дерева и панели
письма — константы (TREE_W 250 / PANE_W 470), компоновку подстроить под
себя нельзя. Схема окна не меняется: список остаётся виртуальным,
DOM не участвует в кадре жеста.

## Решения

- **Веса, не пиксели**: как в Soroka, хранятся веса (f64) трёх панелей;
  px считаются в `layout()` от ширины клиента пропорционально — при
  ресайзе окна компоновка сохраняет пропорции (аналог flex-grow).
- **Жест**: сплиттер — дочернее окно класса `SorokaNativeSplitter`
  (6px, курсор IDC_SIZEWE). WM_LBUTTONDOWN → SetCapture; WM_MOUSEMOVE
  пересчитывает веса пары (математика dragSplit Soroka 1:1: сумма весов
  пары сохраняется, clamp 110px) и шлёт главному окну WM_SIZE — дерево
  и список переложиваются мгновенно.
- **WebView2 вне кадра жеста** (неснижаемое правило WORKFLOW): на время
  перетаскивания границы «список|тело» панель письма прячется
  (SetIsVisible(false)), bounds обновляются один раз после отпускания
  (SetIsVisible(true) + финальный layout). Перетаскивание «дерево|список»
  панель письма не трогает вовсе — она не попадает в кадр жеста.
- **Сохранение**: `%APPDATA%\Soroka\layout.json` (serde_json) — свой файл,
  с данными Soroka не конфликтует; load при старте, save по отпусканию
  мыши и по двойному клику. Нет APPDATA/файла — дефолт Soroka.
- **Сброс**: двойной клик по сплиттеру возвращает весам пары дефолт
  (как dblclick в bindSplit* Soroka).
- **Свободная перестановка панелей** (drag&drop панелей между рядами,
  сворачивание в полосы — TASK-012 в Soroka) — НЕ входит в срез: это
  отдельная большая задача по запросу владельца; здесь компоновка — один
  фиксированный ряд, как в шипе Фазы 0.

## Проверено

- Сборка/тесты/clippy: cargo build --release, cargo test (55 passed /
  0 failed / 1 ignored), cargo clippy --all-targets -- -D warnings — чисто.
- Смоук-тест: приложение запускается, окно живёт, закрывается корректно.
- Перетаскивание проверено синтетическими сообщениями
  (WM_LBUTTONDOWN/WM_MOUSEMOVE/WM_LBUTTONUP): drag границы «список|тело»
  дал ровно математику dragSplit Soroka (list 1.2443 → 1.3698,
  reading 2.023 → 1.8975 — сумма весов пары сохранена); drag
  «дерево|список» + двойной клик вернули паре дефолт. layout.json
  записывается по отпусканию мыши и по dblclick; повторный запуск
  стартует с сохранённой компоновкой (оба выхода — код 0).
- Живая проверка мышью — за владельцем: drag обоих сплиттеров, двойной
  клик (сброс), поведение при ресайзе окна.
- **Мерцание при drag сплиттеров исправлено (v0.3.7):** причина — шесть
  отдельных SetWindowPos на каждый шаг мыши (дети перерисовывались по
  одному, фон окна стирался между ними) и TreeView без двойной
  буферизации. Меры: батч BeginDeferWindowPos/DeferWindowPos/EndDefer-
  WindowPos в layout() (одна перерисовка на шаг), WS_EX_COMPOSITED на
  главном окне, TVS_EX_DOUBLEBUFFER дереву.
- **Мерцание осталось — раунд 2, найден корень (v0.3.10):** фикс v0.3.7
  бил вслепую: в exe **вообще не было манифеста** (проверено
  llvm-readobj --coff-resources по кросс-сборке: секция ресурсов пуста),
  а без манифеста с зависимостью от Microsoft.Windows.Common-Controls
  6.0 загрузчик отдаёт программе comctl32 **5.82**. Расширенные стили
  двойной буферизации (LVS_EX_/TVS_EX_/HDS_DOUBLEBUFFER) — фичи
  **v6 (Vista+)** и без него молча не работают: дерево и список честно
  стирались и перерисовывались на каждый шаг мыши, WS_EX_COMPOSITED
  положения не спасал. Меры:
  - `app.manifest` + `build.rs`: манифест (comctl32 v6, PerMonitorV2)
    встраивается link.exe (`/MANIFEST:EMBED /MANIFESTINPUT`) — только
    для MSVC-таргетов; gnu-кросс-сборка в песочнице линкуется rust-lld
    без манифеста (она для проверок, не доставляется). Если link.exe
    забракует флаги — запасной путь: .rc (`1 24 "app.manifest"`) +
    rc.exe через embed-resource.
  - главное окно: **WS_CLIPCHILDREN** — родитель никогда не рисует
    поверх детей, его стирание фона не мелькает сквозь панели;
    **WS_EX_COMPOSITED убран** — с WebView2-ребёнком (ускоренная
    отрисовка вне WM_PAINT) композиция сама источник вспышек.
  - шапка списка (SysHeader32): HDS_DOUBLEBUFFER (в windows-крейте
    константы нет — 0x0001 из commctrl.h).
  - v6 включает темы контролов: дерево/список/шапка переведены на
    subtheme DarkMode_Explorer (тёмная) / Explorer (светлая) в
    apply_theme — без этого шапка и скроллбары стали бы светлыми.
  - сглаживание drag: WM_MOUSEMOVE только запоминает x и взводит
    таймер 15 мс — раскладку применяет тик (~66 Гц), а не каждое из
    до 1000 событий/с; отпускание дожимает последний x.
  - сплиттер и статус-бар: WM_ERASEBKGND → 1 (весь клиент — в WM_PAINT).
  Ожидаемый побочный эффект v6 (не баг): кнопки/поля диалогов пишутся
  темами current (аккуратнее классики 5.82), главное окно осталось
  тёмным (DarkMode subtheme). Проверка AutoClaw обязательна по чек-листу
  ниже — если мерцание живо, план Б: резиновая полоса вместо live-drag
  (двигаем только сплиттер, раскладка по отпусканию).
- **Живая проверка фикса v0.3.10 (AutoClaw, чек-лист):** (1) сборка
  прошла — манифест в exe: `dumpbin /headers POSmail.exe` или поиск
  строки «Common-Controls» в exe; (2) drag обоих сплиттеров — рябь/вспышки
  отсутствуют, дерево и список перерисовываются целыми кадрами; (3)
  ресайз окна — без мерцания; (4) перетаскивание быстрой мышью (взмах)
  — ровно, отставания нет; (5) двойной клик — сброс весов без артефактов;
  (6) вид: шапка списка и скроллбары тёмные в тёмной теме, светлые в
  светлой; в диалогах кнопки стали themed (ожидаемо); (7) выделение
  писем, поиск, трей — регрессий нет; (8) оба выхода — код 0.
- **Раунд 3 (v0.3.12): разбор внешнего ревью — что уже закрыто, что
  долечиваем.** Владелец принёс независимый аудит по срезу v0.3.10 (два
  бага: compose-мерцание и сплиттер-мерцание). По текущему main оба
  корня уже закрыты и проверены: compose — v0.3.11 (TASK-N08, живая
  проверка AutoClaw 2026-11-19: ресайз пятью шагами без «призраков»),
  манифест — v0.3.10 (Common-Controls внутри exe — True). Реальные
  остатки из ревью — этот срез:
  - **WS_CLIPSIBLINGS** всем детям главного окна (замыкание child, поле
    поиска, оба сплиттера) и редактора: при DeferWindowPos-батче дети
    на миг перекрываются, и без клиппинга соседей
    перерисовывающийся ребёнок рисует поверх другого — вспышки вдоль
    движущейся границы.
  - **Буферный WM_PAINT** сплиттера и статус-бара (собственные классы):
    кадр собирается в CreateCompatibleDC/CreateCompatibleBitmap и
    вываливается одним BitBlt — прямая экранная отрисовка на каждом
    тике drag показывала промежуточное «фон без хвата».
  - **st.dragging = true сразу в WM_LBUTTONDOWN** сплиттера (раньше
    взводился только первым тиком сглаживания): закрыто окно до 15 мс,
    в котором layout() мог тронуть bounds WebView2.
  - **Манифест и для gnu-таргета**: build.rs компилирует app.manifest
    windres'ом (кросс-binutils) в COFF-объект с секцией .rsrc и
    передаёт линковщику; windres не найден — cargo:warning и сборка без
    манифеста (check/clippy в чистой песочнице не ломаются). MSVC-путь
    (link.exe /MANIFEST:EMBED) не менялся — проверен AutoClaw.
    Проверено на кросс-сборке песочницы: `objdump -h` — секция .rsrc
    0x3b0 в POSmail.exe, строки Common-Controls/PerMonitorV2 внутри
    (раньше gnu-сборка была без манифеста вовсе).
  Из ревью осознанно не взято: (1) снятие CS_HREDRAW|CS_VREDRAW с
  главного окна — эти стили срабатывают только при изменении размера
  самого окна, drag сплиттера они не задевают, а ресайз уже проверен
  AutoClaw в v0.3.10 («без мерцания»); (2) RedrawWindow(RDW_ALLCHILDREN
  | RDW_UPDATENOW) после батча — принудительный синхронный ремонт всех
  детей сам источник вспышек, обнажившиеся полосы закрывают
  EndDeferWindowPos + WM_ERASEBKGND главного. Резиновая полоса (план Б
  из ревью и v0.3.10) остаётся в запасе, если живая проверка найдёт
  остаточную рябь.
- **Диалоги настроек/ящика — то же лечение v0.3.11 (v0.3.13):** ревью
  справедливо заметило, что account_dlg.rs и settings_dlg.rs болели
  той же болезнью, что compose до v0.3.11 — голый класс без кисти
  (hbrBackground NULL, ни WM_ERASEBKGND, ни WM_PAINT), 10–11 отдельных
  SetWindowPos на каждый WM_SIZE, нет WS_CLIPCHILDREN и минимального
  размера. Оба диалога получили паттерн редактора v0.3.11:
  - CS_HREDRAW|CS_VREDRAW классу, WM_ERASEBKGND — заливка палитрой
    темы (LRESULT(1)), WM_PAINT — валидация кадра;
  - WS_CLIPCHILDREN окну, WS_CLIPSIBLINGS детям;
  - layout() — один батч BeginDeferWindowPos/…/EndDeferWindowPos
    (резерв — по одному);
  - WM_GETMINMAXINFO: настройки 460×350, ящик 500×360 — контролы
    больше не наезжают друг на друга;
  - WM_CTLCOLORSTATIC/EDIT/LISTBOX палитрой (подписи, пояснение ключа
    и статус читаются в тёмной теме; поля — текст на поверхности) +
    subtheme DarkMode_Explorer/Explorer у полей и combobox;
  - кисти в стейте, освобождаются в WM_DESTROY;
  - смена темы меню при открытом диалоге — на лету: WM_APP_DLG_THEME
    из set_theme главного окна (как WM_APP_COMPOSE_THEME у редактора).
  Кнопки/флажки остаются системной окраски (owner-draw вне объёма,
  как и в редакторе v0.3.11).
