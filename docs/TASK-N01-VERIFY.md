# TASK-N01-VERIFY — собрать шип Фазы 0 и проверить его живьём

Дата: 2026-11-17. Ветка `main`. Версия: `0.1.1`. Предыдущая задача: TASK-N01 (шип).

## Постановка

1. `cargo build --release`. Если не компилируется — править минимально по подсказкам cargo,
   архитектуру не трогать, каждую правку записать в `docs/build-log.txt`. Ориентир:
   tao 0.37 / wry 0.57 используют те же `windows` / `webview2-com`.
2. Запустить `target/release/posmail-native.exe`.
3. Проверить глазами и описать словами: идёт ли список за рамкой при ресайзе на 50 000 строк;
   открывается ли «письмо» в правой панели по двойному клику; Aero Snap и Win+стрелки.
4. Итог: собралось ли с первого раза, что правил, что видно. Коммит и пуш.

## Решения

- Правки — только сигнатуры/пути API под `windows 0.62.2` + `webview2-com 0.39.1`. Виртуальный
  `ListView` (`LVS_OWNERDATA`), WebView2 только в панели письма, раскладка в `WM_SIZE` — не менялись.
- Одна правка сверх компиляции — `SetIsVisible(true)`. Без неё панель письма чёрная (см. «Проверено»),
  то есть пункт 3 постановки не выполнялся. Это не архитектура, а обязательный вызов после создания
  контроллера.
- `docs/build-log.txt` добавлен в `.gitignore`: `docs/WORKFLOW.md` п.3 требует его там, в репозитории
  строки не было. Сам лог не коммитится — перечень правок продублирован здесь и в шапке лога.
- Проверка — программами, а не на словах: реальные `SetWindowPos`/`RedrawWindow`, `SendInput`
  (мышь/клавиатура), снимки экрана. Замеры повторены по 2–3 раза.
- `cargo fmt --check` не трогал: он не чист с самого начала (порядок импортов в строках, которых я
  не касался); форматирование всего файла раздуло бы диф.

## Проверено

### 1. Окно и раскладка

Окно `1418×914` при старте (рамка), DPI 96, один монитор 1920×1080. При размере 1400×900
(клиентская 1384×835): дерево 240 px, список 724 px, панель письма 420 px, статус-бар 20 px.
`LVM_GETITEMCOUNT` у живого окна = **50000** — список действительно на 50 000 элементов,
видимых строк ~60.

Скриншот: дерево с шестью папками, список с колонками «От» / «Тема» / «Дата», панель письма,
статус «50 000 писем в виртуальном списке — тяни край окна». Всё нарисовано, пустых полос нет.

### 2. Ресайз при 50 000 строк — идёт ли список за рамкой

Замеры (200 шагов смены размера подряд, замер каждой перекладки):

| Прогон | среднее на шаг | худший шаг | темп |
|---|---|---|---|
| 1 | 6,91 мс | 16,9 мс | 145 Гц |
| 2 | 6,78 мс | 15,7 мс | 148 Гц |
| 3 | 6,61 мс | 14,8 мс | 151 Гц |

Перекладка + принудительная полная перерисовка (`RedrawWindow` с `RDW_UPDATENOW`):
8,8–17,0 мс на шаг (редкие выбросы до 20–26 мс, машина не пустая: рядом Soroka, браузер, SQL Server).
Одна принудительная перерисовка всего окна: 5,8–7,4 мс.

**Главное — контрольный опыт.** Собрал вариант с `ROWS = 100` и прогнал тот же замер:

| Объём списка | среднее на шаг |
|---|---|
| 100 строк | 6,38 и 6,87 мс |
| 50 000 строк | 7,01 и 6,67 мс |

Разницы нет — время ресайза не зависит от объёма, как и задумано в виртуальном `ListView`.
После опыта `ROWS` возвращён в 50 000, exe пересобран (`LVM_GETITEMCOUNT` снова 50000).

Глазами: при перетаскивании края и угла список перекладывается вместе с рамкой, белых полос и
«отстающего» содержимого не видно; после 8-секундного непрерывного жеста (480 кадров, худший шаг
перекладки 14,0 мс; во втором прогоне 382 кадра, худший 11,8 мс) список, панель и статус-бар стоят
на своих местах, ничего не разъехалось.

Честная оговорка: шаги ресайза подавались из **другого процесса**, поэтому в каждое число входит
межпроцессная доставка `SetWindowPos` и COM-вызов `SetBounds` в WebView2 (это round-trip в процесс
браузера). В реальном перетаскивании рамки раскладка выполняется в своём потоке — то есть это
верхняя оценка, а не стоимость самого `WM_SIZE`.

### 3. Двойной клик по строке

- Клик по строке 0 → в панели заголовок «Тема письма №0 — виртуальный список не боится объёма»,
  мета «Отправитель 0 · 18.11.2026 00:00», в статус-баре «Открыто: Тема письма №0 — …».
- Клик по строке 14 → панель сменилась на «Тема письма №14 …», мета «Отправитель 14 · 18.11.2026 00:14»,
  статус «Открыто: Тема письма №14 — …».

Панель рисует настоящий HTML: заголовок, серая мета-строка, два абзаца, блок с синей полосой слева
и подпись. То есть цепочка `NM_DBLCLK` → `NavigateToString` → отрисовка WebView2 работает.

### 4. Aero Snap и Win+стрелки

| Действие | Геометрия окна | Комментарий |
|---|---|---|
| `Win+Left` | −7, 0, 974×1057 | левая половина (невидимые рамки −7 px) |
| `Win+Right` | 953, 0, 974×1057 | правая половина |
| `Win+Up` | −8, −8, 1936×1066, `zoomed=true` | развёрнуто |
| `Win+Down` | 60, 30, 1400×900 | восстановлено до прежнего размера |
| `Win+Down` ещё раз | −32000, −32000, `iconic=true` | свёрнуто в панель задач |
| Мышь: заголовок к левому краю | −7, 0, 974×1057 | Aero Snap сработал |

Раскладка при snapped-окне (974 px): дерево 240, список ~310, панель 420 — панели не наезжают
друг на друга и не оставляют дыр, письмо в панели остаётся на месте.

Две особенности среды, не приложения:
- вторая Win+стрелка подряд не срабатывает — фокус после снапа забирает системный Snap Assist;
- `Win+Up` из свёрнутого состояния окно не восстановил: фокус в этот момент был на панели задач.
- быстрый «телепорт» курсора к краю экрана снап не вызвал; снап сработал при медленном
  человеческом дрейфе по 6 px до самого края (x=0). Это особенность синтетического ввода.

### 5. Что мешало проверке

Окно несколько раз закрывали **с самой машины**: в трассировке сообщений видно
`WM_SYSCOMMAND 0xF060` (SC_CLOSE) → `WM_CLOSE` → `WM_DESTROY`, код выхода 0. Падения не было —
это обычное закрытие окна пользователем, а не дефект. Трассировка и диагностика после выяснения
причины удалены из `src/main.rs`.

Мелочи раскладки, замеченные глазами (не дефекты задачи):
- колонки 260 + 480 + 150 = 890 px шире списка (724 px при окне 1400), поэтому «Дата» доступна
  только горизонтальной прокруткой;
- ширина панели письма фиксирована (420 px): на половине экрана список сжимается до ~310 px,
  и колонка «Тема» обрезается.

## Осталось

- Ширина панели письма и колонок — пропорциональная раскладка вместо фиксированных 420/260/480/150
  (в Фазе 2, когда появятся реальные письма и настройки вида).
- Проверить на 150 %/200 % DPI: сейчас всё измерено на 96 DPI.
- `Cargo.lock` не в репозитории (лежит неотслеживаемым). Для бинарника его стоит закоммитить —
  тогда зафиксируются ровно те версии, на которых шип проверен.
- `WM_GETMINMAXINFO` ограничивает размер 960×600; сохранение/восстановление геометрии окна — Фаза 2.
