# WORKFLOW — правила работы агента над POS Mail Native

## Общее

1. Один репозиторий, ветка `main`. Задачи: `docs/TASK-NXX-<имя>.md` по шаблону из Soroka (Постановка / Решения / Сделано / Проверено / Осталось).
2. Версии до первого релиза: `0.1.x` — Фаза 0, `0.2.x` — Фаза 1. Коммиты: `feat|fix: v0.X.Y — суть (TASK-NXX)`.
3. Длинные операции (сборка) — фоновым процессом, вывод в `docs/build-log.txt` (в `.gitignore`).

## Сборка и проверки

1. `cargo build --release` — обязательна перед каждым коммитом; результат и размеры артефактов в лог.
2. `cargo test` — модули из Soroka уже покрыты тестами (accounts/store/imap), они должны проходить.
3. `cargo clippy --all-targets -- -D warnings` — держим чисто; предупреждения чиним сразу.

## Специфика кода вне Windows-машины

- Код Фаз 0–1 написан вне Windows-машины, под связку `windows 0.62` +
  `webview2-com 0.39` (те же версии, что у wry 0.57 в Soroka). **Если
  что-то не компилируется из-за сигнатур/путей API — правь минимально по
  подсказкам cargo и запиши каждую правку в `docs/build-log.txt`.**
- Ориентиры для сигнатур: tao 0.37 и wry 0.57 используют ровно эти версии
  `windows`/`webview2-com` — как они вызывают функцию, так и правильно.
- Известные места, где сигнатуры могли измениться: `CreateMenu`/
  `CreatePopupMenu` (голый HMENU или Result), `EnableWindow`/`SetFocus`
  (bool/Result), `NONCLIENTMETRICSW` (может лежать в другом модуле),
  `GetWindowTextW` (срез вместо указателя). Это мелкие правки, не архитектура.

## Архитектурные правила (неснижаемые)

- Не менять схему: виртуальный список `LVS_OWNERDATA` + раскладка в
  `WM_SIZE` + WebView2 только в панели письма и окнах, где владелец явно
  разрешил. DOM не участвует в кадре ресайза.
- Блокирующие операции (IMAP/SMTP/SQLite) — только в рабочем потоке
  (`backend.rs`), никогда в UI-потоке. UI читает только кэш SQLite.
- `src/mail/` — ядро Soroka дословно: не редактировать без отдельной
  задачи владельца. Правки ядра — сначала в Soroka, потом перенос.
- Не добавлять UI-фреймворки (WinUI, native-windows-gui, egui и т.п.) —
  только Win32 через `windows-rs`.

## Порядок задачи

1. Прочитать `docs/PLAN.md` и последний `docs/TASK-*.md`.
2. Сделать, собрать, проверить (для UI — запустить и проверить глазами,
   записать наблюдения в файл задачи).
3. Закоммитить, запушить в `main`. Если сборка или проверки падают — не
   коммитить: показать ошибку и ждать решения владельца.

## Проверка Фазы 1 (критерий из плана)

1. Ящики из `accounts.json` Soroka подхватываются при старте; без ящиков —
   `Ящики → Добавить ящик`, кнопка «Проверить соединение».
2. INBOX синхронизируется при старте; выбор папки показывает письма из кэша
   мгновенно; F5 — обновление с сервера.
3. Выбор письма — тело в правой панели; непрочитанные строки — полужирные и
   становятся обычными после прочтения; клик по вложению сохраняет файл
   в «Загрузки».
4. Ctrl+N — новое письмо, Ctrl+R — ответ (с цитатой), отправка уходит,
   копия появляется в «Отправленные»; при выдернутом сетевом кабеле письмо
   встаёт в очередь и уходит после следующей успешной синхронизации.
5. Del — удаление в корзину сервера; Ctrl+U — прочитано/не прочитано.
6. Ресайз окна при открытом реальном ящике — без лагов (проверка Фазы 0
   на реальных данных).
