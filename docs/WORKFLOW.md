# WORKFLOW — правила работы агента над POS Mail Native

## Общее

1. Один репозиторий, ветка `main`. Задачи: `docs/TASK-NXX-<имя>.md` по шаблону из Soroka (Постановка / Решения / Сделано / Проверено / Осталось).
2. Версия до первого релиза: `0.1.x`. Коммиты: `feat|fix: v0.1.X — суть (TASK-NXX)`.
3. Длинные операции (сборка) — фоновым процессом, вывод в `docs/build-log.txt` (в `.gitignore`).

## Сборка и проверки

1. `cargo build --release` — обязательна перед каждым коммитом; результат и размеры артефактов в лог.
2. `cargo test` — когда появятся тесты (модули из Soroka уже покрыты частично).
3. `cargo clippy --all-targets -- -D warnings` — держим чисто; предупреждения чиним сразу.

## Специфика шипа (Фаза 0)

- Код шипа написан вне Windows-машины, под связку `windows 0.62` +
  `webview2-com 0.39` (те же версии, что у wry 0.57 в Soroka). **Если
  что-то не компилируется из-за сигнатур/путей API — правь минимально по
  подсказкам cargo и запиши каждую правку в `docs/build-log.txt`.**
  Архитектуру (виртуальный список, WebView2 только в панели, раскладка в
  WM_SIZE) не менять.
- Ориентиры для сигнатур: tao 0.37 и wry 0.57 используют ровно эти версии
  `windows`/`webview2-com` — как они вызывают функцию, так и правильно.

## Порядок задачи

1. Прочитать `docs/PLAN.md` и последний `docs/TASK-*.md`.
2. Сделать, собрать, проверить (для UI — запустить и проверить глазами,
   записать наблюдения в файл задачи).
3. Закоммитить, запушить в `main`. Если сборка или проверки падают — не
   коммитить: показать ошибку и ждать решения владельца.

## Железные правила

- Не менять `src/main.rs` архитектурно без отдельной задачи владельца.
- Не добавлять UI-фреймворки (WinUI, native-windows-gui, egui и т.п.) —
  только Win32 через `windows-rs`; WebView2 — только для тела письма и
  окон, где владелец явно разрешил.
- Не тащить код из Soroka с UI-логикой: переносим только модули из списка
  «Переносится как есть» в `docs/PLAN.md`.
