# TASK-N02 — Фаза 1: почтовый каркас

Дата: 2026-11-18. Предыдущая задача: TASK-N01 (Фаза 0, шип скорости —
владелец подтвердил: «проверил, работает быстро»).

## Постановка

Подключить к нативной оболочке почтовое ядро Soroka так, чтобы выполнить
критерий Фазы 1 из `docs/PLAN.md`: **прочитать и ответить на реальное письмо,
вся переписка видна**. Архитектуру ресайза из Фазы 0 не трогать.

## Решения

### Перенос ядра (без изменений, 5 517 строк)

`src/mail/` — файл в файл из `src-tauri/src/mail/` Soroka 0.46.57:
`accounts.rs` (397), `imap.rs` (1 657), `store.rs` (2 231), `smtp.rs` (337),
`body.rs` (418), `contacts.rs` (440), `parser.rs` (6), `mod.rs` (31).
Ядро не знало о Tauri — замены кода не потребовалось. Версии крейтов
скопированы из Cargo.toml Soroka (imap 3.0.0-alpha.15, rusqlite 0.40,
lettre 0.11, mail-parser 0.11, ammonia 4…). Edition 2024 — в ядре есть
let-цепочки. `tracing` оставлен как no-op (логи ядра).

`src/ai/gigachat.rs` — шим: только структура `AiAnalysis` (serde), которая
лежит в колонках `soroka.db`. Сетевая часть GigaChat — Фаза 3, reqwest
не тянем.

База и настройки общие с Soroka: `%APPDATA%\Soroka\soroka.db`,
`accounts.json` — клиент открывает их напрямую (как в плане миграции).

### Бэкенд вместо команд Tauri (`src/backend.rs`)

Порт оркестрации из `commands/mod.rs`:

| Команда Soroka | Куда переехала |
|---|---|
| `sync_inbox` | `sync_folder` (INBOX: заголовки + список папок + `save_sync`) |
| `sync_folder` | `sync_folder` (остальные: `save_folder_sync`) |
| `get_message_body` | `fetch_body` (кэш → сеть → кэш) |
| `set_seen` | `set_seen` |
| `delete_message` | `delete_message` (move_to_trash + кэш) |
| `save_attachment` | `save_attachment` (в «Загрузки») |
| `send_mail` | `send_mail` (+ `save_sent_copy`, очередь TASK-089) |
| `flush_outbox` | `flush_outbox` (после успешной синхронизации INBOX) |
| `test_login` | `Job::TestLogin` для окна ящика |

Транспорт: один рабочий поток (как The Bat!) + mpsc-канал задач
`Job` → выполнение (блокирующий IMAP/SMTP/SQLite не в UI) → события
`MailEvent` в общую очередь → `PostMessageW(WM_APP_MAIL)` → wndproc
главного окна разбирает. Ответы окнам-редакторам (отправка, тест
соединения) идут адресными PostMessage c `Box` в lParam.

### Оболочка

- `main.rs` — окно Фазы 0 + меню (Почта/Папка/Ящики/Файл), ускорители
  (Ctrl+N/R/Shift+R/F, Del, Ctrl+U, F5), диспетчер сообщений.
- `ui.rs` — дерево ящиков/папок (кэш → выбор INBOX → мгновенный показ),
  виртуальный список уже не «Резиновый», а `Vec<MessageHeader>` из кэша;
  непрочитанные — полужирным (NM_CUSTOMDRAW, шрифт NONCLIENTMETRICS),
  маркер вложений — колонка «Вл.»; тёмный HTML-шаблон письма с шапкой,
  вложениями (клик → сохранение) и санитизированным телом.
- `compose.rs` — окно написания: Кому/Копия/Тема, тело (multiline Edit),
  вложения (GetOpenFileNameW, мультивыбор, MIME по расширению), отправка
  через `Job::SendMail`; ответ/пересылка предзаполняются с цитированием.
- `account_dlg.rs` — окно ящика: email/пароль/IMAP/SMTP, «Проверить
  соединение» (Job::TestLogin), сохранение через `upsert_account`
  (accounts.json общий с Soroka — ящики подхватываются сами).

### Что осталось за кадром Фазы 1 (по плану — Фаза 2)

FTS5-поиск, черновики, настройки «в трей»/автопроверка (check_interval_sec

BCC-поле, Tab-навигация в редакторе (IsDialogMessage), IDLE-пуш,

### Сборка на машине владельца (2026-11-18, v0.2.1 → v0.2.3)

- Первый `cargo build --release`: 45 ошибок в 6 файлах (код писался вне Windows).
  Исправлено 22 правки, все — сигнатуры/пути API под windows 0.62 + одна
  фича (`Win32_UI_Controls_Dialogs` для `GetOpenFileNameW`). Архитектура не
  менялась. Полный перечень — `docs/build-log.txt`.
- По предупреждению `unused variable id` нашёлся дефект: `child()` не передавал
  ID контрола в `CreateWindowExW` — все контролы получали ID 0 и `WM_COMMAND`
  по `IDC_*` не срабатывал (кнопки окна письма и ящика). Исправлено.
- `cargo build --release` — чисто, `target/release/POSmail.exe` 3 712 512 байт (v0.2.3).
- `cargo test` — 56 тестов: 55 прошло, 1 ignored, 0 упало (тесты ядра Soroka).
- `cargo clippy --all-targets -- -D warnings` — **чисто** с v0.2.3. Долг закрыт в два захода:
  v0.2.2 — `allow(dead_code)` на `mod mail` и 7 игнорированных `Result` приведены к `let _ =`;
  v0.2.3 — 20 оставшихся замечаний: `too_many_arguments` у `child()`, redundant closure,
  collapsible_if через let-chains (edition 2024), лишние касты, `Default::default()`
  с присваиванием, неиспользуемые поля (`SyncDone::account_id`, `SendOutcome::queued`,
  `TreeSlot`), needless_borrow в ядре — через `allow` на модуле, сам `src/mail/` не правился.
- Запуск exe намеренно не выполнялся: при старте идёт синхронизация реальных

### Проверка живьём (2026-11-18, v0.2.4)

Запускал на машине владельца с реальными ящиками (`accounts.json`:
`reznikov_a@mail.ru`, `russiaimperia@yandex.ru`).

Работает:

- ящики и папки подхватываются из `accounts.json` (путь берётся из `%APPDATA%`;
  при запуске из окружения без APPDATA приложение честно пишет «Ящики не настроены» —
  так и случилось при первом моем запуске);
- INBOX синхронизируется (25 → 27 писем), список виртуальный, непрочитанные жирным,
  после открытия письма жирность снимается;
- выбор письма — HTML-тело в панели (таблицы, картинки), статус «тема (кэш)»;
- Ctrl+N — окно письма (поля 650 px, тело 740×313, кнопки на месте);
  Ctrl+R — Кому и «Re: …» заполняются;
- ресайз при открытом реальном ящике: 150 шагов, 8,7 мс на шаг (~115 Гц),
  единичный выброс 70 мс; панели не разъезжаются.

Найдено и исправлено в v0.2.4:

1. `wide::wptr` возвращал `PCWSTR` на ВРЕМЕННЫЙ `Vec<u16>` — `SetWindowTextW` читал
   уже освобождённую память. Симптом: тело ответа = **3 символа мусора** вместо
   цитаты, «Кому» = 37 символов вместо 34. Заменено на `wide::set_window_text`
   (буфер живёт до конца вызова), `wptr` удалён.
2. Цитата ложилась одну строку: многострочный EDIT в Win32 делит строки только
   по CRLF, а `quote_body` собирал через `\n`. Теперь CRLF — 30 строк / 3340 символов,
   цитата построчно с «> ».

Не проверялось сознательно: отправка (ушло бы реальное письмо), Del (корзина
сервера), Ctrl+U, вложения, очередь при обрыве сети.

С v0.2.4 отправку можно проверять безопасно: в `accounts.json` есть два тестовых
ящика (`reznikov_a@mail.ru` и `russiaimperia@yandex.ru`) — письма гоняются между
ними, см. `docs/WORKFLOW.md`, раздел «Тестовые ящики».

### Отправка и приём между тестовыми ящиками (2026-11-18)

Проверено вживую: Ctrl+N → Кому `russiaimperia@yandex.ru`, тема «POS Mail test v0.2.4
- sending check», тело из двух строк → «Отправить» → диалог «Письмо отправлено.».
Через 15 с (F5) письмо появилось в INBOX второго ящика от `reznikov_a@mail.ru`,
открылось в панели: тема, отправитель, получатель, дата и текст тела — целые,
без искажений (косвенно подтверждает и починку `wptr`).

Замечание к разбору: сразу после отправки в дереве у mail.ru на миг исчезла
строка «Отправленные» (статус показывал «Пароли и разное: 8 писем») — то есть
пересборка дерева после `save_sent_copy` теряет одну папку; после перезапуска
«Отправленные» снова на месте. Нужна отдельная проверка `rebuild_tree` после
отправки (не блокирует приём/отправку).

### Чистка clippy (v0.2.2)

Закрыт долг v0.2.1 — 72 предупреждения:

- `dead_code` ядра: `#[allow(dead_code)]` на объявлении `mod mail;` в
  `main.rs` — строка объявления, сам `src/mail/` не тронут (правило WORKFLOW).
  Обоснование: ядро перенесено дословно, неподключённые API (контакты, IDLE,
  пресеты провайдеров) заводятся в Фазах 2–3 по плану; до того предупреждения
  неинформативны. Снять `allow` — одновременно с подключением этих API.
- 7 игнорированных `Result` (`account_dlg.rs`: отмена/закрытие/сохранение
  ящика; `compose.rs`: отмена/успешная отправка/закрытие): все —
  `DestroyWindow`/`PostMessageW` на пути закрытия окна, где осмысленной
  обработки ошибки нет; приведены к стилю остального кода (`let _ = ...`).

Поведение не менялось, `src/mail/` не редактировался. Проверка на машине
владельца: `cargo build --release`, `cargo test`, `cargo clippy --all-targets
-- -D warnings` — должно стать чисто; единичные non-dead_code хвосты, если
останутся, чинить минимально по WORKFLOW с логом в `docs/build-log.txt`.
